# Workflow Design Principles

用这份 reference 设计或审查需要人机协作的 pi capability。它是 checklist，不是 runtime checkpoint；默认不在每次交互中展示。

## 一、可感知产出，不汇报苦劳

AI 做的脏活必须转化成用户可判断的价值产出。

默认展示：

- 已产生的 artifact、diff、issue draft、PR body、decision record 或可运行结果。
- 当前结论、关键取舍、剩余风险和验证结果。
- 有意义的排除项，例如“没有改 GitHub workflow”。

默认不展示：

- 搜了多少文件、读了多少行、跑了多少轮这类原始劳动量。
- 没有帮助用户判断的过程流水账。
- 为了显得努力而重复解释内部步骤。

## 二、递减主动性

AI 主动性随任务复杂度和决策风险递减。

4-level 梯度：

1. 直接做：低风险、目标清楚、可逆的小任务。
2. 做，但确认交付边界：实现路径清楚，但 commit、PR、发布或外部副作用前需要确认。
3. 按计划做，遇到新判断停住：已有计划或 issue，但出现 scope、风险、取舍变化时停住。
4. 先对齐、地图或计划：目标模糊、影响面大、会改变 workflow 或长期规则。

设计 capability 时，要写清楚它默认处在哪一级，以及升级或降级的触发条件。

## 三、显式人类判断

人的高价值工作应表现为“当前需要用户判断什么”，而不是流程标签。

好的表达：

- “请判断这两个边界是否符合你的使用习惯。”
- “这里有一个 scope change，需要你决定是否纳入本 PR。”
- “这条建议合理但不阻塞，我建议转后续 issue。”

避免表达：

- “进入人类高价值判断阶段。”
- “等待 human-in-the-loop。”
- “我完成了大量探索工作。”

## 审查问题

- 用户看到的是可判断产出，还是 AI 的劳动过程？
- capability 是否说明了不同风险等级下的主动性边界？
- 需要用户判断的地方是否自然、具体、可回答？
- 是否把这些原则复制进其他 workflow，造成未来漂移？
